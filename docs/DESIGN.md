# MMStudio 官网设计方案

## 1. 文档效力

本文档是 MMStudio 官网产品设计、视觉设计、内容规划和技术架构的唯一事实来源，所有实现工作都必须遵循本文档。

开始任何实现工作之前，必须依次完成：

1. 更新本文档，说明计划进行的设计或架构变更。
2. 根据本文档的优先级更新项目根目录下的 `TODO.md`。
3. 在修改代码或配置之前，取得用户的明确授权。

项目协作说明和设计文档不得通过绝对路径或其它方式引用仓库外部文档；维持项目所需的规则必须直接写入仓库内的对应文档。

## 2. 项目标识

- 团队简称：**MMStudio**
- 英文全称：**MeaninglessMeaningStudio**
- 中文名称：**妄言真意**
- 当前核心产品：**Deadpan / 积案拂尘**
- 官网域名：**mmstdio.games**
- GitHub 组织：<https://github.com/mmstudio-games>
- 官网仓库：<https://github.com/mmstudio-games/mmstudio>
- 当前游戏站点：<https://deadpan.hydroroll.team/>

MMStudio 目前没有正式 Logo。在正式 Logo 提供之前，官网只能使用纯文字名称，不得自行制作、生成或使用替代 Logo。

《积案拂尘》的正式 Logo 将在后续提供。在此之前，产品展示应使用文字排版，且不得将其表述为正式产品 Logo。

## 3. 产品目标

官网应当承担以下职责：

1. 建立统一、清晰的 MMStudio 网络品牌形象。
2. 将《积案拂尘》作为团队当前的核心产品进行展示。
3. 提供游戏入口和 GitHub 组织主页入口。
4. 支持中文和英文访问。
5. 为产品详情、开发动态、团队资料和联系方式预留可扩展结构。

当前交付重点是主页。其它页面应预留统一的页面壳层和路由结构，但不得编造尚未确认的内容。

## 4. 信息架构

### 当前最高优先级页面

- `/` —— 主页

### 预留路由

- `/games/deadpan` —— 《积案拂尘》产品页
- `/news` —— 开发动态和版本记录
- `/about` —— 团队资料，内容暂缓
- `/contact` —— 联系信息，当前不设置表单

Cloudflare 正式公开入口确定后，应保证直接访问上述预留路由时页面仍能正常打开。

## 5. 主页结构

主页由以下部分组成：

1. 全局导航：包含 MMStudio 文字标识、产品和动态入口、语言切换及指向 `mmstudio-games` 组织的 GitHub 链接。
2. 团队首屏：以 MMStudio 和“妄言真意”名称为主体，不使用虚构 Logo。
3. 《积案拂尘》核心产品展示：提供直接进入游戏的主要操作。
4. 三项简洁的设计理念：分别介绍自由盘问、动态案卷和以人为核心的叙事方向。
5. 最新讯号区域：展示当前开发状态。
6. 简洁页脚：展示团队名称和版权信息。

在相关资料得到确认之前，不展示团队介绍、成员名单、联系表单或虚构的团队历史。

## 6. 视觉方向

### 视觉参考

视觉系统参考当前《积案拂尘》游戏站点。通过浏览器检查确认，游戏站点采用以报刊和案卷为核心的视觉体系，主要特征包括：

- 深褐色桌面和档案背景；
- 暖色旧纸张表面；
- 接近黑色的褐色油墨；
- 克制使用的朱红色印章和状态强调色；
- 直角几何造型；
- 编辑排版风格和大量分隔线。

工作室官网应与游戏站点保持视觉关联，但不能直接复制游戏站点复杂的报纸版式。官网整体应更加平静、现代，并适合承载工作室级别的品牌形象。

### 暂定配色

- 深色档案背景：`#2b2116`
- 纸张高光：`#f5efdf`
- 纸张阴影：`#ebe0c8`
- 木质中间色：`#5e4c34`
- 木质边缘色：`#4a3c2c`
- 深色边缘：`#3d3020`
- 印章和状态红：约 `#8f2f21`

在取得正式截图或官方视觉资产后，可以进一步校准上述颜色。

### 形状与布局规则

- 只使用 shadcn/ui 的 **Sera** 样式。
- 默认圆角值为零。
- 避免圆角卡片、过多胶囊形导航、玻璃拟态，以及与纸张或档案材质无关的装饰性渐变。
- 使用分隔线、分栏、页码、档案编号和文字层级组织内容。
- 即使参考信息密集的报刊设计，工作室官网也应保留充足留白。
- 动效保持克制，并支持 `prefers-reduced-motion`。

### 字体

- 主要标题使用具有编辑感的衬线字体。
- 界面和正文使用无衬线字体。
- 案件编号、日期和档案信息使用等宽字体。
- 在选定正式中文网页字体之前，中文内容必须提供可靠的系统字体回退方案。
- 英文超大标题必须根据自身内容栏宽度缩放，不能以整个视口宽度作为唯一字号依据。
- 连续相同字母不得因负字距发生明显重叠；标题字距应在保持紧凑排版感的同时保证每个字形清晰可辨。

## 7. 响应式设计

- 桌面端：使用鲜明的双栏构图和较完整的产品展示舞台。
- 平板端：保留不对称层级，同时合并过窄的分栏。
- 移动端：使用单栏信息流、可读的标题尺寸，避免横向溢出，并提供适合触控的导航。
- 在所有断点下，核心操作和语言切换功能都必须可用。

## 8. 无障碍要求

- 导航和控件必须支持键盘操作。
- 必须提供清晰可见的焦点状态。
- 提供“跳至正文”链接。
- 纯图标控件必须具有明确的无障碍名称。
- 跳转链接、导航标签、语言切换和弹层控件等辅助文本必须跟随当前语言，不能只提供英文名称。
- 正文和关键控件以达到 WCAG AA 对比度为目标。
- 支持减少动态效果。
- 使用正确的标题层级和语义化页面区域。

## 9. 技术架构

- 包管理器和 JavaScript 运行时：Bun
- 开发语言：TypeScript
- 用户界面框架：React
- 路由：React Router
- 组件系统：shadcn/ui，Sera 样式，Base UI 基础组件
- 样式系统：Tailwind CSS v4 和语义化 CSS 变量
- 客户端状态：Zustand，仅用于真正需要跨页面共享的用户偏好
- 国际化：react-i18next
- 表单：如未来确有需要，使用 react-hook-form 并结合数据结构校验
- 托管集成：仓库已连接 Cloudflare Workers production build；正式公开入口和自定义域名仍待确认
- 自定义域名：`mmstdio.games`
- 代码格式化与静态审查：Biome

### 组件规范

- 所有组件文件名必须使用 `kebab-case`，例如 `site-layout.tsx` 和 `home-page.tsx`。
- shadcn 基础组件统一放在 `src/components/ui`。
- 业务组件必须按功能或页面分类，不能放入 `components/ui`。
- 在未来路由架构获得明确批准之前，路由级页面统一放在 `src/pages`。

### Tailwind CSS 使用规范

- 页面布局、间距、尺寸、排版、颜色、边框、定位、状态和响应式规则必须优先使用 Tailwind 工具类，并直接写在对应的 TSX 组件中。
- 不得在全局样式表中为普通页面布局建立 `.hero-grid`、`.product-copy` 一类传统业务选择器。
- `src/index.css` 应尽可能只保留 Tailwind、shadcn 和字体导入、shadcn 语义令牌、必要的全局元素规则及浏览器级无障碍规则。
- 必须优先使用 Tailwind 的任意值、任意属性、响应式变体和状态变体，不能仅因数值特殊就改写为传统 CSS。
- 复杂纹理、渐变、阴影和伪元素效果也应优先使用 Tailwind 任意值与变体直接写入组件；不得仅通过 `@layer utilities` 包装普通 CSS 来规避 Tailwind 优先要求。
- 只有确实无法合理放入组件的全局行为，才允许保留直接 CSS，并应说明其全局必要性。
- 静态 `className` 应直接传入 Tailwind 字符串；只有条件类名、多段样式拼接，或较长类名需要按职责分组提高可读性时，才使用 shadcn/ui 提供的 `cn()` 工具函数。
- 不得使用 `const pagePadding = "..."` 一类变量保存或拼接 Tailwind/CSS 字符串；需要复用或分组的类名应在对应元素的 `cn()` 调用中就地表达，避免样式定义脱离使用位置。

### Biome 规范

- 使用 Biome 统一承担格式化、Lint 和持续集成审查，移除 Oxlint 配置与依赖。
- 全局缩进使用2个空格，与当前工作区保持一致，不使用 Biome 默认的 Tab 缩进。
- JavaScript、TypeScript 和 JSX 使用单引号、按需分号和尾随逗号。
- Biome 配置中的 schema 版本必须与锁文件实际解析的 CLI 版本一致，避免本地和 CI 出现迁移提示。
- CSS 格式化必须启用，并开启 `css.parser.tailwindDirectives`，使 Biome 正确解析 Tailwind CSS v4 的 `@theme`、`@apply`、`@custom-variant` 等语法。
- 本地 `lint` 脚本使用 Biome 检查，另提供可写入的格式化脚本；CI 使用只读检查，不在流水线中自动修改文件。

### 状态与内容规范

- 不得将路由状态或静态内容放入 Zustand。
- 只持久化确实需要在刷新后保留的用户偏好。
- 翻译键应按语义区域组织。
- 不得编造尚未确认的团队或产品信息。

## 10. 部署与搜索优化

- 仓库内的 GitHub Actions 只负责安装依赖、Biome 审查和生产构建，不执行部署；仓库外部已连接 Cloudflare Workers production build 集成。
- `mmstdio.games` 当前尚未完成 DNS 和公开入口验证；在获得明确授权前，不修改 Cloudflare、DNS 或部署状态。
- Cloudflare 的正式公开入口确定后，必须验证客户端路由回退，保证直接访问预留路由可用。
- 主页需要配置规范链接、页面描述、Open Graph 元信息和适当的主题色；切换语言时，页面标题、描述和 Open Graph 标题与描述应同步更新。
- 产品图片和社交分享图片必须等到取得正式素材后再添加。
- GitHub Actions 使用 `oven-sh/setup-bun@v2` 安装 Bun canary；当前项目不得固定为不存在的稳定版 `1.4.0`。
- 仓库文件中不保留 GitHub Pages 上传、权限、环境或部署任务；GitHub 仓库设置中残留的历史 `github-pages` environment 待获得外部状态变更授权后清理。
- 不生成 GitHub Pages 专用的 `404.html`，也不保留 `public/CNAME`。

## 11. 版本控制基线

- 当前可运行的主页、项目规范文档、依赖锁文件和部署准备文件应作为仓库的初始化基线统一提交。
- 初始化提交只建立本地版本历史，不包含远程仓库配置、推送或部署操作。
- 默认分支使用 `main`，后续变更应在明确范围内形成可追溯提交。
- 规范远程仓库为 `https://github.com/mmstudio-games/mmstudio`；旧的 `Meaningless-Meaning-Studio/mmstudio` 地址只作为 GitHub 重定向存在，不再写入配置或页面链接。
- Tailwind 样式架构重构和 Bun canary 工作流修复已作为独立提交推送至 `origin/main`，用于同步远程仓库并触发后续持续集成检查。
- Biome 迁移和纯检查 CI 已作为独立提交推送至 `origin/main`，用于验证远程环境中的格式审查与生产构建。

## 12. 变更控制流程

所有非临时任务必须遵循以下流程：

1. 检查当前仓库及适用的项目说明。
2. 更新 `docs/DESIGN.md`，写明计划进行的设计或架构变更。
3. 更新 `TODO.md`，并保持与设计方案一致的优先级顺序。
4. 请求或确认用户已经明确授权修改代码和配置。
5. 只实现已授权的范围。
6. 根据风险执行适当的代码检查、类型检查、构建和界面验证。
7. 再次更新 `TODO.md`，记录已完成和仍待处理的工作。

不修改项目文件的临时诊断和只读检查，不要求更新上述文档。
