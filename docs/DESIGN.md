# MMStudio 官网设计方案

## 1. 文档效力

本文档是 MMStudio 官网产品设计、视觉设计、内容规划和技术架构的唯一事实来源，所有实现工作都必须遵循本文档。

开始任何实现工作之前，必须依次完成：

1. 更新本文档，说明计划进行的设计或架构变更。
2. 根据本文档的优先级更新项目根目录下的 `TODO.md`。
3. 在修改代码或配置之前，取得用户的明确授权。

项目协作说明和设计文档不得通过绝对路径或其它方式引用仓库外部文档；维持项目所需的规则必须直接写入仓库内的对应文档。

## 2. 项目标识

- 团队简称：**MMStudio**
- 英文全称：**MeaninglessMeaningStudio**
- 中文名称：**妄言真意**
- 当前核心产品：**Deadpan / 积案拂尘**
- 官网域名：**mmstdio.games**
- GitHub 组织：<https://github.com/Meaningless-Meaning-Studio>
- 当前游戏站点：<https://deadpan.hydroroll.team/>

MMStudio 目前没有正式 Logo。在正式 Logo 提供之前，官网只能使用纯文字名称，不得自行制作、生成或使用替代 Logo。

《积案拂尘》的正式 Logo 将在后续提供。在此之前，产品展示应使用文字排版，且不得将其表述为正式产品 Logo。

## 3. 产品目标

官网应当承担以下职责：

1. 建立统一、清晰的 MMStudio 网络品牌形象。
2. 将《积案拂尘》作为团队当前的核心产品进行展示。
3. 提供游戏入口和 GitHub 组织主页入口。
4. 支持中文和英文访问。
5. 为产品详情、开发动态、团队资料和联系方式预留可扩展结构。

当前交付重点是主页。其它页面应预留统一的页面壳层和路由结构，但不得编造尚未确认的内容。

## 4. 信息架构

### 当前最高优先级页面

- `/` —— 主页

### 预留路由

- `/games/deadpan` —— 《积案拂尘》产品页
- `/news` —— 开发动态和版本记录
- `/about` —— 团队资料，内容暂缓
- `/contact` —— 联系信息，当前不设置表单

在 GitHub Pages 环境中直接访问上述预留路由时，页面仍应能够正常打开。

## 5. 主页结构

主页由以下部分组成：

1. 全局导航：包含 MMStudio 文字标识、产品和动态入口、语言切换及 GitHub 链接。
2. 团队首屏：以 MMStudio 和“妄言真意”名称为主体，不使用虚构 Logo。
3. 《积案拂尘》核心产品展示：提供直接进入游戏的主要操作。
4. 三项简洁的设计理念：分别介绍自由盘问、动态案卷和以人为核心的叙事方向。
5. 最新讯号区域：展示当前开发状态。
6. 简洁页脚：展示团队名称和版权信息。

在相关资料得到确认之前，不展示团队介绍、成员名单、联系表单或虚构的团队历史。

## 6. 视觉方向

### 视觉参考

视觉系统参考当前《积案拂尘》游戏站点。通过浏览器检查确认，游戏站点采用以报刊和案卷为核心的视觉体系，主要特征包括：

- 深褐色桌面和档案背景；
- 暖色旧纸张表面；
- 接近黑色的褐色油墨；
- 克制使用的朱红色印章和状态强调色；
- 直角几何造型；
- 编辑排版风格和大量分隔线。

工作室官网应与游戏站点保持视觉关联，但不能直接复制游戏站点复杂的报纸版式。官网整体应更加平静、现代，并适合承载工作室级别的品牌形象。

### 暂定配色

- 深色档案背景：`#2b2116`
- 纸张高光：`#f5efdf`
- 纸张阴影：`#ebe0c8`
- 木质中间色：`#5e4c34`
- 木质边缘色：`#4a3c2c`
- 深色边缘：`#3d3020`
- 印章和状态红：约 `#8f2f21`

在取得正式截图或官方视觉资产后，可以进一步校准上述颜色。

### 形状与布局规则

- 只使用 shadcn/ui 的 **Sera** 样式。
- 默认圆角值为零。
- 避免圆角卡片、过多胶囊形导航、玻璃拟态，以及与纸张或档案材质无关的装饰性渐变。
- 使用分隔线、分栏、页码、档案编号和文字层级组织内容。
- 即使参考信息密集的报刊设计，工作室官网也应保留充足留白。
- 动效保持克制，并支持 `prefers-reduced-motion`。

### 字体

- 主要标题使用具有编辑感的衬线字体。
- 界面和正文使用无衬线字体。
- 案件编号、日期和档案信息使用等宽字体。
- 在选定正式中文网页字体之前，中文内容必须提供可靠的系统字体回退方案。
- 英文超大标题必须根据自身内容栏宽度缩放，不能以整个视口宽度作为唯一字号依据。
- 连续相同字母不得因负字距发生明显重叠；标题字距应在保持紧凑排版感的同时保证每个字形清晰可辨。

## 7. 响应式设计

- 桌面端：使用鲜明的双栏构图和较完整的产品展示舞台。
- 平板端：保留不对称层级，同时合并过窄的分栏。
- 移动端：使用单栏信息流、可读的标题尺寸，避免横向溢出，并提供适合触控的导航。
- 在所有断点下，核心操作和语言切换功能都必须可用。

## 8. 无障碍要求

- 导航和控件必须支持键盘操作。
- 必须提供清晰可见的焦点状态。
- 提供“跳至正文”链接。
- 纯图标控件必须具有明确的无障碍名称。
- 正文和关键控件以达到 WCAG AA 对比度为目标。
- 支持减少动态效果。
- 使用正确的标题层级和语义化页面区域。

## 9. 技术架构

- 包管理器和 JavaScript 运行时：Bun
- 开发语言：TypeScript
- 用户界面框架：React
- 路由：React Router
- 组件系统：shadcn/ui，Sera 样式，Base UI 基础组件
- 样式系统：Tailwind CSS v4 和语义化 CSS 变量
- 客户端状态：Zustand，仅用于真正需要跨页面共享的用户偏好
- 国际化：react-i18next
- 表单：如未来确有需要，使用 react-hook-form 并结合数据结构校验
- 托管平台：GitHub Pages
- 自定义域名：`mmstdio.games`

### 组件规范

- 所有组件文件名必须使用 `kebab-case`，例如 `site-layout.tsx` 和 `home-page.tsx`。
- shadcn 基础组件统一放在 `src/components/ui`。
- 业务组件必须按功能或页面分类，不能放入 `components/ui`。
- 在未来路由架构获得明确批准之前，路由级页面统一放在 `src/pages`。

### 状态与内容规范

- 不得将路由状态或静态内容放入 Zustand。
- 只持久化确实需要在刷新后保留的用户偏好。
- 翻译键应按语义区域组织。
- 不得编造尚未确认的团队或产品信息。

## 10. 部署与搜索优化

- GitHub Actions 负责构建并发布 `dist` 目录。
- GitHub Pages 必须支持直接访问客户端路由。
- `public/CNAME` 必须包含 `mmstdio.games`。
- 主页需要配置规范链接、页面描述、Open Graph 元信息和适当的主题色。
- 产品图片和社交分享图片必须等到取得正式素材后再添加。

## 11. 版本控制基线

- 当前可运行的主页、项目规范文档、依赖锁文件和部署准备文件应作为仓库的初始化基线统一提交。
- 初始化提交只建立本地版本历史，不包含远程仓库配置、推送或部署操作。
- 默认分支使用 `main`，后续变更应在明确范围内形成可追溯提交。

## 12. 变更控制流程

所有非临时任务必须遵循以下流程：

1. 检查当前仓库及适用的项目说明。
2. 更新 `docs/DESIGN.md`，写明计划进行的设计或架构变更。
3. 更新 `TODO.md`，并保持与设计方案一致的优先级顺序。
4. 请求或确认用户已经明确授权修改代码和配置。
5. 只实现已授权的范围。
6. 根据风险执行适当的代码检查、类型检查、构建和界面验证。
7. 再次更新 `TODO.md`，记录已完成和仍待处理的工作。

不修改项目文件的临时诊断和只读检查，不要求更新上述文档。
